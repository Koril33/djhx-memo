## 3. 桌面空白页与 Ctrl+W

### 3.1 当前实现与可行性

[App.svelte](../desktop/src/App.svelte) 的 Ctrl+W 直接调用 `request_hide`；[原生命令](../desktop/src-tauri/src/main.rs)复用关闭按钮的 lifecycle：保存成功后，有托盘则隐藏，无托盘则退出，保存失败留在窗口内。0.1.11 明确将 Ctrl+W 定义为窗口级关闭，新的两段行为属于一次有意的产品语义调整。

目前 `editor.open(null)` 表示新建草稿；右侧仍挂载编辑器，没有独立的“无打开文档”状态。因此不能简单用 `editor.note == null` 判断空白页：未首次保存的草稿也没有 note ID，但其中可能已有用户输入。

建议增加明确的编辑区模式，例如 `welcome / draft / note`，而不改变 Markdown 数据格式或创建一条虚假的“欢迎笔记”。空白页只属于 Windows/Linux，Android 维持现有列表/编辑导航。

### 3.2 建议交互

| 当前状态 | 操作 | 建议结果 |
|---|---|---|
| 已打开笔记，含预览/回收站只读笔记 | Ctrl+W | 完成可提交输入的保存，关闭当前编辑会话，回到空白页 |
| 新建草稿已有内容 | Ctrl+W | 按既有保存规则落为笔记，成功后回空白页；不丢弃草稿 |
| 新建草稿没有可保存内容 | Ctrl+W | 回空白页，不为欢迎页创建空笔记 |
| 空白页 | Ctrl+W | 调用既有 `request_hide`，继续继承托盘、安装屏障和无托盘降级规则 |
| 保存失败/编辑代次冲突未处理 | Ctrl+W | 保留正文和当前页面，显示既有重试/另存出口，不先切空白页 |
| 输入法组合中、模态框内 | Ctrl+W | 维持当前守卫，不抢输入、不穿透模态框 |
| 任意正常页面 | 标题栏 X / Alt+F4 / 托盘退出 | 建议保持既有窗口级 lifecycle，不强制增加空白页步骤 |

保存必须等 [EditorSession](../desktop/src/lib/editor-session.ts) 的 flush 成功；组件卸载或清空绑定值不能代替保存。切换过程应串行处理，并在短暂提交期间保护输入，避免用户在 flush 与卸载之间输入的字符被遗漏。按键自动重复必须忽略：长按一次 Ctrl+W 不能先关闭笔记又立即隐藏窗口。

关闭时还需清理笔记内查找、旧编辑器 API、选中项和焦点；空白页不应保留“列表选中 A、右侧却无文档”的误导状态。关闭只影响会话，不删除笔记，不撤销同步，不清空 outbox。

### 3.3 是否符合常见操作习惯

“关闭当前文档”与“关闭应用窗口”分层符合编辑器习惯。例如 VS Code 官方快捷键表区分 Close Editor 与 Close Window；各平台具体按键并非完全相同，不能称所有主流编辑器都采用相同的两次 Ctrl+W。[VS Code 官方说明](https://code.visualstudio.com/docs/reference/default-keybindings)

对于已有关闭到托盘行为的单窗口笔记应用，这一调整合理：第一次关闭当前工作对象，第二次收起应用。需要通过空白页提示让第二步可发现，并保留单实例启动/托盘恢复兜底。

空白页建议仅有三项，不放新闻、教程卡片或最近文件堆叠：

- 新建笔记 — `Ctrl+N`。
- 搜索笔记 — `Ctrl+Shift+F`。
- 关闭窗口 — `Ctrl+W`；按实际托盘可用性说明“隐藏到托盘”或“退出”。

**不建议把“搜索笔记 Ctrl+F”直接作为提示。** 当前 Ctrl+F 是笔记内查找，无笔记时窗口级处理无动作。若要空白页的 Ctrl+F 转为全局搜索，可以实现，但需明确增加上下文特例；建议本版继续保持 Ctrl+F / Ctrl+Shift+F 的分工。

### 3.4 待定的导航边界与建议默认值

建议冷启动进入空白页；从托盘恢复则恢复隐藏前的页面，不重新关闭仍打开的笔记。托盘“新建笔记”直接进入草稿。切换空间/分区后进入空白页，避免自动创建草稿或打开不相关笔记；删除当前笔记后进入空白页。已有导入成功后的打开行为保留。

这些入口应在实施前一起定稿，尤其是“启动是否自动打开上次笔记”；目前不能把建议默认值写成维护者已批准的结论。不需要为了空白页引入多标签页或会话恢复持久化。

## 4. 全局搜索范围、来源标签与挤压问题

### 4.1 当前“账号”不是所有账号

[Engine::search_notes](../core/src/lib.rs)当前支持 `current / all_local / account`，其中 `account` 只搜当前选中的账号；没有激活账号时返回空。它还支持显式 `space_ids`，但没有正式的“所有本机与账号空间”枚举值；把 `kind` 随意改为 `all` 会落入当前空间分支。

因此只隐藏过滤按钮并不能实现需求。建议在 core 定义清晰的“所有可搜索空间”语义，由 core 枚举本机已有的 `local` 与 `account` profile，统一包含 `deleted=true` 的普通删除笔记。可以扩展范围枚举；若复用 `space_ids`，也必须把空间选择规则写进契约，避免两端各写一套不同的“全部”。两端 UI 不再提供范围或回收站开关。

该搜索仍是**本地搜索**：覆盖所有保留在本机的账号空间副本，不会搜索从未登录/同步到本机的账号，也不会临时联网抓取完整云端内容。提示“仅搜索本机已有内容，含账号副本和回收站”应常驻，不能因为删除过滤器而一并删除。

### 4.2 “所有”的边界

| 数据 | 建议行为与需说明的边界 |
|---|---|
| 本机空间、所有本机保留的账号空间 | 全部参与，不依赖当前激活空间；这是本轮明确要求 |
| 普通回收站 | 固定包含；来源账号/空间和“回收站”同时显示，打开后保持只读与原有恢复规则 |
| 已退出登录或凭据过期的账号缓存 | 建议按仍保留在本机的账号空间纳入，允许离线检索；需确认跨账号总览的隐私预期，不把登出当作本地数据已删除 |
| 恢复空间 `recovery` | 建议继续排除，避免旧归档与有效副本重复出现；用户列举的范围没有明确要求扩展到恢复归档，若要纳入须另定只读标识和跳转行为 |
| 彻底删除完成的正文 | 继续排除，不为搜索恢复或保留已清除的正文；pending/rejected 状态继续服从彻底删除契约 |
| 不在本机的云端内容 | 不包含，不新增服务端搜索 API |

现有 core 账号登出主要移除凭据并切回本机空间，不删除账号笔记库；上述边界需要明确，避免用户误以为“退出登录就不会被全局搜索看到”。不应为搜索结果跳转自动登录另一个账号或把它的笔记复制到当前空间。

### 4.3 结果来源与跳转

现有 `SearchHit` 有 `profile_id / space_kind / deleted`，没有账号显示名。桌面 `spaceBadge()` 还会用“回收站”覆盖空间标签，无法同时表达“哪个账号的回收站”；Android 只显示泛称“账号空间”。

建议来源独立于删除状态，例如：`本机空间`、`alice · example.org`、`alice · example.org · 回收站`。示例为合成账号。同名账号必须以服务器区分；长名称允许省略并提供完整可访问名称，窄屏元信息可换行，不能挤压正文。展示内容不含 token、设备凭据或内部数据库路径。

账号元数据可由 `profile_id` 对应 registry 快照，也可由 core 返回安全的来源描述；建议统一返回/管理来源快照，确保空间切换或重命名期间仍对应同一结果，字段选择在接口定稿时确定。

跨空间打开结果需先成功保存当前编辑内容，再切换到结果所属空间并读取最新笔记；删除/彻底删除等搜索后变化必须在打开时重查，失败不能悄悄打开错误空间的同 ID 笔记。回收站结果应呈现回收站上下文，不能因为来源跳转失去只读保护。

桌面结果 key 已使用 `note_id + profile_id`；Android LazyColumn 目前只用 `note_id`。全账号聚合时必须使用复合身份，覆盖同一 UUID 出现在不同账号/空间的情况，避免重复 key 或结果错位。

### 4.4 桌面挤压的实际原因

用户已确认问题出现在 Windows/Linux，截图与当前 CSS 的压缩行为一致。[GlobalSearch.svelte](../desktop/src/GlobalSearch.svelte) 中：

- 结果容器是纵向 Flex，`max-height: 380px`，`overflow-y: auto`。
- 每条结果也是 Flex item，默认 `flex-shrink: 1`；全局 button 的 `min-height: 36px`。
- 条目未禁止收缩，标题/元信息仍绘制，摘要可被压为 0，内容越过条目背景进入下一条。

本轮用原始组件 CSS、全局 CSS、合成标题/两行摘要/元信息构造隔离页面，在 Windows Edge headless、1000×800 窗口测量 DOM 几何。未接入用户数据库，未修改产品源码。

| 合成结果数 | 原样式条目高度 | 原样式摘要高度 | 相邻内容重叠数 | 仅在验证页面禁止条目收缩后的重叠数 |
|---|---|---|---|---|
| 3 | 112.375px | 38.375px | 0 | 0 |
| 10 | 36px | 0 | 9 | 0 |
| 50 | 36px | 0 | 49 | 0 |

在相同 fixture 中禁止条目收缩后，10/50 条结果均保持 112.375px，通过容器正常滚动。这确认了可直接复现的 CSS 原因；不是因为单字搜索不受支持，也不应通过限制查询长度或减少结果数来掩盖。

建议修正方向：结果条目保持内容所需高度，不参与纵向压缩；建立清晰的容器高度、`min-height: 0` 与滚动链；按需要限制标题/摘要行数，来源信息换行；键盘上下移动到视口外结果时滚动使其可见。取消过滤行会改变可用高度，但不会自动消除 Flex 收缩根因。

Android 使用原生 Compose LazyColumn，没有这一 CSS 根因，不能据本次验证宣称它也出现相同缺陷。新增账号标签后，Android 单行元信息 Row 的宽度仍需单独验收。

### 4.5 数量、性能与错误

“全部范围”与“显示全部命中”是两个问题。当前合并排序后返回 top 50，并用 `truncated` 提示。建议 0.1.13 保留这一数量策略、明确提示“显示前 50 条，请细化关键词”；如果希望加载更多，应另行确定跨空间稳定分页，不能仅删除截断提示。

多账号扩大了开库、扫描、打分和 segments 构造成本。现有 blog 基准只测内存 SQLite 的候选 SQL，不含多库打开、完整正文打分、IPC 和界面渲染，不能拿约 1.6ms 的 P99 宣称全账号端到端已达标。

实施时需验证：多空间中单字高频查询、至少 50 条命中、冷/热查询；快速改词/关闭面板/切空间后旧响应不覆盖新结果；排序平局保留稳定的空间身份兜底；一个库失败不能显示为“没有结果”。建议明确部分成功时的“结果不完整＋具体空间失败”提示，若沿用整次失败也须可重试且不伪报空结果。不能吞错后给出完整搜索的暗示。

## 5. Android Markdown 列表续写

### 5.1 原因已确定

桌面 [Editor.svelte](../desktop/src/Editor.svelte) 加载 `markdown()`。锁定的 `@codemirror/lang-markdown@6.5.2` 默认启用 Markdown keymap，将 Enter 绑定到 `insertNewlineContinueMarkup`。这不是 core 自动补全，也不是 Markdown 渲染器在修改正文。

Android [SourceEditor.kt](../android/app/src/main/java/app/djhx/memo/SourceEditor.kt) 使用 `AndroidView` 内的原生 EditText。当前 InputConnectionWrapper 只转发组合输入/commit 并跟踪 composing；TextWatcher 负责传出正文、高亮和查找刷新，没有列表上下文判断或回车续写命令。因此两端表现不同属于平台编辑能力未对齐，不能归因于 Android 键盘未配置好。

本轮直接执行已安装的 CodeMirror 命令，确认以下结果：

| 输入位置在末尾 | 命令结果 |
|---|---|
| `- item` | 新行加入 `- ` |
| `1. item` / `9. item` | 新行加入 `2. ` / `10. ` |
| 空列表项 `- ` / `1. ` | 删除空标记、退出列表上下文；普通回车回退行为由编辑器处理 |
| 围栏代码块中的 `- item` | Markdown 续写命令不处理，保留普通换行 |

该验证是依赖命令级验证，未操作实际桌面窗口或 Android 输入法。

### 5.2 建议的最小行为

Android 先对齐桌面基础有序/无序列表：有效列表项末尾按回车，沿用缩进和无序符号，有序编号按当前项递增；空列表项再回车退出列表。代码块、普通段落、转义符号和非列表文本继续普通换行。

嵌套列表、任务列表、引用内列表、`1)` 编号的优先级需定稿。建议先覆盖基础列表和常见缩进；如果把任务项纳入，应新建未勾选的 `[ ]`，不复制已完成的 `[x]` 状态。不要把手动编号列表整体重排作为此次隐含需求。

只处理用户的一次回车意图，不在每次 `afterTextChanged` 时重写全文，不对粘贴的多行文本批量补符号。实现应覆盖软键盘的 newline 提交与硬件键盘路径，并避免同一次回车被处理两遍；中文候选确认 Enter 不能被当作列表换行。

正文、插入的换行/前缀、光标和原生撤销应构成一致的编辑动作；验证选区替换、行中回车、缩进、组合 span、撤销/重做与自动保存。编辑命令可在 Android 平台层实现，不需要为此改写整套编辑器或引入 WebView；若选择新解析依赖，再按 ADR/许可规则独立评估。

## 6. Windows/Linux 标题栏

### 6.1 代码能确认的原因

[tauri.conf.json](../desktop/src-tauri/tauri.conf.json)只设置窗口标题、尺寸等属性，未关闭原生装饰；[Linux 配置](../desktop/src-tauri/tauri.linux.conf.json)只覆盖包名/DEB 设置，没有 title 对齐规则。原生 `set_presentation` 调用 `window.set_title(...)`，不绘制 logo/title 的布局。

Tauri 的 `decorations` 默认值为 true，即使用窗口边框和标题栏；当前锁定 tao 的 Linux 实现把 title 与 decorated 属性交给 GTK Window。由此可确认：用户看到的是 Windows 与 Linux 桌面环境的原生窗口装饰差异，并非 Svelte 内的同一行布局写了两个不同的对齐方式。[Tauri 官方配置](https://v2.tauri.app/reference/config/#windowconfig)

Linux 具体由窗口管理器还是 GTK 客户端装饰绘制，取决于桌面环境、主题和 X11/Wayland。GTK HeaderBar 本身允许左右放控件、标题相对整栏居中，与用户描述相符；但本项目没有显式创建该 HeaderBar，不能据此断言用户环境一定走该控件，也不能说所有 Linux 都必须居中。[GTK 官方说明](https://docs.gtk.org/gtk3/class.HeaderBar.html)

0.1.12 删除的是客户端列表顶部的品牌行，属于窗口内容区；它没有修改上述系统标题栏。

### 6.2 三种选择

| 选择 | 效果与代价 | 建议 |
|---|---|---|
| 保留原生装饰 | logo/title 内容一致，位置遵循 OS/桌面主题；窗口菜单、拖动、缩放和辅助功能由系统提供 | 推荐用于 0.1.13；将差异视为平台适配，不为位置差异单独改窗口框架 |
| Linux 单独定制 GTK 标题区 | 可以控制 Linux 内容布局，但需处理 GTK/桌面环境差异，也不保证与 Windows 像素一致 | 若确实要求 Linux 左对齐，先做独立原型验证；不修改用户全局 GNOME/KDE 设置 |
| 两端自定义标题栏 | 可稳定实现左侧 logo＋名称，视觉控制最多；同时承担系统交互与无障碍维护 | 只有“完全一致”是明确目标时再立项，中到较高工作量 |

自定义标题栏不是一条 `text-align: left`：需要验证拖动区、按钮点击、双击最大化、窗口系统菜单、边缘缩放、Windows Snap、DPI、多屏、Linux Wayland/X11、键盘与辅助功能。关闭按钮仍须调用既有安全 lifecycle，不得绕过保存、托盘或更新安装屏障。新增窗口操作权限也需逐项限定。

本轮未启动 Linux VM，未在用户桌面环境重现标题栏像素；结论边界是“原生装饰机制已确认，具体 Linux 装饰提供者未实测”。

### 8.3 最新发布流程与本版边界

当前流程是：审核合并并同步公开 main/tag → [release.yml](../.github/workflows/release.yml)构建、Windows Tauri package 签名与 Android 原证书签名、创建草稿 → 维护者核验并公开 → [catalog.yml](../.github/workflows/catalog.yml)签更新目录并生成官网部署包 → 维护者本机运行[部署脚本](../scripts/deploy-website.sh)，完成线上检查。

[ADR-0017](adr/0017-github-actions-ci.md)之后的 [ADR-0019](adr/0019-update-catalog-website-ci.md)已将 catalog 签名移入 CI；不能继续按部分旧文档理解为“CI 仅生成未签名包、目录钥不进入 CI”。package 与 catalog 签名用途仍分离，服务器写权限仍不交给 CI。Linux 继续手动 DEB 安装，不由本轮扩大自动更新范围。

发布前还需注意以下已存在的实现/证据边界，本轮只记录，不修改工作流：

1. `release` job 的 `needs` 目前只有四类构建，不含 `test`，因此草稿存在并不证明测试 job 必然通过；桌面前端测试、Android 单元/仪器测试也不能由打包成功替代。按本地入口完成对应检查并记录实际结果。
2. 目录工作流对 APK 证书“读取失败”当前只是 warning，成功读到但不匹配才失败；不能把它描述成所有情况下都完成了证书交叉验证。正式包仍需实际证书与覆盖升级核验。
3. 笔记库已是 schema 4，但更新目录的 `schema_min/schema_max`、生成脚本和旧更新器仍严格使用 3。不能只把数字改成 4，否则旧更新器会拒绝；发布准备应单独澄清该兼容字段与新增迁移的关系，验证 0.1.10/0.1.11/0.1.12 升级链。该观察不是“已证实不能更新”。
4. 远程部署脚本自动健康检查主要检查首页 200，不等于设计中的三平台下载及目录验签全覆盖；0.1.13 应记录公开下载、目录序号/有效期、签名与真实安装结果。脚本存在、Release 有 bundle 也不能证明生产回滚已验证。
5. 工作流若另行修订，仍必须由维护者审阅后再打 tag，不由同一修改者自行发版。本轮不触发 CI 发布、签名或部署。
