## 0. 贯穿全局的基础机制

CodeMirror 6 的 `keymap` 命中时调用 `preventDefault()`，但**不 `stopPropagation()`**，事件仍冒泡到 `<svelte:window on:keydown>`。**[假设]** 需 5 分钟 spike 实测确认。

据此，`App.svelte` 全局处理器统一加三道守卫，顺序固定：

1. `if (e.defaultPrevented) return;`
2. `if (e.isComposing || e.keyCode === 229) return;`
3. 上下文判定：目标是否在 `input/textarea/contenteditable` 内、是否有模态框、是否多选态。

硬规则：全局处理器**绝不用 `capture:true`**；应用接管的组合键**必须显式 `preventDefault()`**（否则 WebView2/WebKitGTK 可能触发"另存为"等原生行为）；修饰键判定在 Windows/Linux 只认 `ctrlKey`，不把 `metaKey` 当 Mod；预留 `isMac` 开关位。

## 1. Ctrl+W → 隐藏到托盘

**推荐**：职责划分——Rust `CloseRequested` 是唯一关闭策略执行点；前端只做意图识别，Ctrl+W → `appWindow.close()`。四个入口（标题栏 X、Alt+F4、任务栏关闭、Ctrl+W）行为天然一致。

**托盘不可用降级（AGENTS 硬约束）**：Tauri Linux 走 libayatana-appindicator，创建返回 `Ok` ≠ 图标真实可见（vanilla GNOME / 禁用扩展会静默消失）。分级：Windows `hide()`；Linux 默认 `minimize()`（保留任务栏入口），"关闭到托盘"做成显式设置项（默认关）；单实例插件必须"再次启动 show+unminimize+set_focus 已有窗口"作兜底。

**冲突与风险**：
- 🔴 Readline 肌肉记忆（最高）：Linux/终端 Ctrl+W = 删除前一个词。缓解：绑 Ctrl+Backspace 删词、Linux 默认 minimize、设置项可关。
- 🟡 浏览器肌肉记忆双刃：Ctrl+W 在浏览器是"关标签页"。**产品语义需拍板**：本项目不做 tab，定 Ctrl+W = 窗口级（未来若做 tab 改语义）。
- 🟡 保存失败：隐藏≠退出，但仍建议阻止隐藏，与"保存失败阻止退出"同一心智模型。
- 🟡 模态框内忽略；IME 组合期守卫 2 覆盖；Wayland 恢复焦点需实测（xdg-activation）。

**第一版**：Ctrl+W → `appWindow.close()`；Windows hide / Linux minimize；flush 失败不隐藏；模态框忽略；单实例唤起；首次隐藏提示一次；不做 Ctrl+Shift+W、不做可配置键位 UI。

## 2. Ctrl+F → 笔记内查找

**推荐**：直接用 `@codemirror/search`，不自研。`search({top:true})` + `searchKeymap`（Mod-f / F3 / Shift-F3 / Mod-g / Mod-Shift-g / Mod-Alt-g / Escape 关面板 / Mod-d 选中下一个）+ `highlightSelectionMatches()`。`searchKeymap` 放 `defaultKeymap` 之前。

**冲突**：`defaultKeymap`/`standardKeymap` 不绑 Mod-f/Mod-g/F3；真正会打架的是未引入的 `emacsStyleKeymap`（保持不引入）。**[假设]** 以当前 CM6 版本键表为准，升级依赖复查。

**是否窗口级拦截 Ctrl+F**：编辑器聚焦不拦截（CM 吃掉，守卫 1 兜底）；未聚焦且有笔记 → 聚焦 + `openSearchPanel`；无笔记 → 转发全局搜索。预览态 → 切编辑态再查（WebView2/WebKitGTK 无原生 Ctrl+F，且给渲染 DOM 做 range 高亮成本高）。

**风险**：
- 🟡 IME 下 Enter 二义（上屏 vs 查找下一个）：自定义 `createPanel` 自守 `isComposing`。**[假设]** 默认面板未处理。
- 🟡 Escape 三重语义：靠守卫 1 + 优先级链（面板 > 失焦 > 关菜单/取消多选），须写测试。
- 🟡 笔记内查找是纯前端行为，不受"v1 仅字面子串"契约约束；建议默认 `caseSensitive:false`（与全局搜索对齐）；替换区域只读态显隐 **[假设]** 需验证。

## 3. Ctrl+Shift+F → 全局搜索

**触发**：`Mod-Shift-f` 在 searchKeymap/defaultKeymap 均未占用，编辑器聚焦不消费、冒泡到全局，无需特殊优先级。**UI**：命令面板式居中浮层（复用模态框 Escape + Tab 焦点陷阱），非常驻侧栏。

**范围数据模型（重要）**：回收站是 note 的**状态**而非 space，不应与"本机/账号"做成三选一互斥。应拆成两个正交维度：空间集合单选（当前/全部本机/账号）+ "包含回收站"独立 checkbox。

**两个 UI 硬要求**：(1) "账号空间"第一版是纯本地搜已同步内容，必须显式说明"仅搜索已同步到本机的笔记"；(2) 回收站命中只允许预览/恢复，不直接编辑。

**core 动作**：新增 `search_notes`，不扩展 `list`（list 契约是稳定排序+分页+单空间，混入会变"可选字段汤"）。

**高亮表示法（最容易埋 bug）**：Rust UTF-8 字节偏移 ↔ JS UTF-16 ↔ Kotlin UTF-16 不一致，中文/emoji 必错位。**强烈推荐 core 返回已切分 segments 数组 `[{text, hit}]`**，前端零偏移运算、零编码换算。

**片段生成在 core 端**：避免 1000×2KiB≈2MiB 跨 IPC 序列化；core 持有原文、能正确处理 UTF-8 边界与 CJK 窗口；片段必须与匹配语义一致。**不用 FTS5 `snippet()`/`highlight()`**：trigram token 边界与字面子串语义不同，且 <3 字符 LIKE 路径无 FTS 行可用，两条路径会不一致。

**相关性**：不用 bm25（trigram + 字面子串下意义有限，且 <3 字符 LIKE 路径拿不到 bm25，两条路径不可比）。在 core 对已召回候选做确定性打分：标题命中（大权重）、标题完整/前缀匹配（加成）、命中位置（行首/词边界/标题行）、命中次数（`log(1+n)` 封顶）、长度归一化、新鲜度（温和衰减，封顶 ≤20%）。**打分只影响排序不影响召回**，写进 spec。

**排序必须有全序 tiebreaker**：`ORDER BY score DESC, updated_at DESC, note_id ASC`。

**分页/防抖/增量**：跨库 offset 无法下推（各库 top-N 合并第 N ≠ 任一库第 N）。v1 不做 offset：每库候选上限 200 → 内存合并 → top 50 → `truncated` 提示。防抖 120–180ms + 请求序号/AbortController 丢弃过期响应。多空间 Rust 侧顺序执行即可，无需并行。

**性能达标路径**：预算 IPC 5–15ms + 查询 5–20ms + 打分 <5ms + 片段 <10ms + 渲染 <20ms。真正风险在查询次数与数据搬运：①两阶段查询（先 SELECT id/title/updated_at 召回打分，再对 top 50 读 content 生成片段）；②防抖+过期丢弃压到 <5 次/秒；③每库候选上限 200；④≥3 走 trigram、<3 走 LIKE；**FTS5 `MATCH` 查询串需正确引号转义（空格/`"`/`*`/`:`），有单测覆盖**；⑤基准按空间数量而非仅笔记数测。**衔接设计**：打开结果 → 注入 query 到 CM `setSearchQuery` + `findNext` 定位首命中。

## 4. 快捷键冲突矩阵（要点）

- 模态框内统一屏蔽 Ctrl+N/W/F/Shift+F，仅放行 Ctrl+S。
- 🔴 `indentWithTab` 造成键盘焦点陷阱：Tab 被编辑器吃掉。**Escape 需做逃生口**：优先级面板 > 编辑器失焦 > 关菜单/取消多选。
- 🟡 Ctrl+Shift 在 Windows 可被配置为切换输入语言，Ctrl+Shift+F 可能顺带切布局；备选 Ctrl+Shift+P / Ctrl+K。
- ✅ 确认：仅 webview `keydown`，不引入 tauri-plugin-global-shortcut；窗口未聚焦/隐藏后三个快捷键全失效，唯一恢复入口是托盘/单实例唤起——这把"托盘可用性检测"升格为**正确性前提**。

## 5. Android

**桌面先行，Android 延后**，但分开看：全局搜索第二批跟进（触屏用户也需跨笔记搜索，入口是 UI 图标）；笔记内查找明确延后（Compose 无内置 find，成本高、频率低）；Ctrl+W 不适用（对应系统返回手势）。

**关键依赖 [假设]**：Android 是否复用同一 Rust core。若复用（UniFFI），`search_notes` 一次实现双端共享，Android 只缺 UI，跟进成本低；若独立 Kotlin 实现，打分/片段/转义需重写，契约漂移风险高——应等桌面契约冻结，把排序/片段规则写成可测试规格 + 共享测试向量。

Material 3 有 `SearchBar`/`DockedSearchBar` 可作全局搜索入口；结果高亮用 `AnnotatedString` + `SpanStyle` 消费 core segments（无 UTF-8↔UTF-16 换算）。

## 风险与待确认假设清单

🔴 高：R1 Linux 托盘图标可能静默不可见（hide 后不可找回）；R2 高亮偏移 Rust/JS/Kotlin 错位（用 segments 消除）；R3 账号空间仅搜本地副本被误判为数据丢失（UI 显式说明）；R4 FTS5 MATCH 转义不足（转义函数+单测）；R5 Readline 误触 Ctrl+W（Linux minimize + Ctrl+Backspace + 可关）。

🟡 中：R6 Ctrl+W 产品语义（窗口级 vs 关当前笔记）；R7 Escape 优先级链（indentWithTab 逃生口）；R8 无笔记时 Ctrl+F 行为；R9 回收站是否独立 checkbox（建议改）；R10 笔记内查找功能面（默认面板 vs createPanel 精简）；R11 Windows Ctrl+Shift 切输入语言；R12 跨库不做 offset（top 50 + 截断）是否可接受。

🟢 需实测：A1 CM6 keymap 命中 preventDefault 但不 stopPropagation（方案基石）；A2 CM 默认面板是否处理 isComposing；A3 CM6 当前版本 defaultKeymap 不绑 Mod-w/Mod-f/Mod-g/F3；A4 替换区域只读态显隐；A5 Wayland 托盘点击可靠恢复；A6 WebView 对 Ctrl+S/F/W 原生行为被 preventDefault 压制；A7 Android 是否复用 Rust core；A8 回收站与正常笔记是否同表带 deleted 标记；A9 典型用户空间数量（P95 基准按空间数设计）；A10 单笔记最大体积（1MiB 上限，需片段/CM 上限保护）。

**一句话结论**：三项功能技术路径都不复杂，真正工程风险在三处——`defaultPrevented` 守卫机制是否成立（A1）、Linux 托盘不可靠导致 Ctrl+W 违反"窗口必须可找回"硬约束（R1）、跨语言高亮偏移（R2，用 segments 一次性消除）。建议先做 A1+A5 spike，并在开工前定 R6（Ctrl+W 语义）与 R7（Escape 优先级）。
