## 1. 讨论范围与建议顺序

| 主题 | 当前证据 | 初步建议 |
|---|---|---|
| M2 大笔记停顿 | 独立 API35 样本已复现 | 优先处理源码页，再处理预览与复杂块；先测量再优化 |

## 2. M2：先保证大笔记可编辑、可保存

### 2.1 现有证据与待定位处

独立样本：960,000 UTF-8 字节、20,000 行标题；导入公共桥接 228 ms，打开实际源码编辑页至空闲 135,561 ms，主线程心跳最大间隔 131,692 ms。样本未打开预览，因此“只换 LazyColumn”不足以修好 M2。结果是 API35/debug 的单次观测，不是 release/arm64 指标或 P95。

源码位置：

- [SourceEditor.kt](../android/app/src/main/java/app/djhx/memo/SourceEditor.kt)：setText、四组全文正则、span 清除/添加、update 和原生长文本布局。
- [MarkdownPreview.kt](../android/app/src/main/java/app/djhx/memo/MarkdownPreview.kt)：remember 中同步解析、非惰性 Column 和块组合。
- [CodeHighlights.kt](../android/app/src/main/java/app/djhx/memo/CodeHighlights.kt) 与 [core highlight.rs](../core/src/highlight.rs)：共享代码高亮已有异步调用/防抖和 128 KiB UTF-8 上限，不能误认所有高亮都没有阈值；Android 本地 Markdown 正则是另一条路径。

后续先用 tracing/profiling 分离 setText、正则、span、布局、解析、组合和桥接/复制成本。不能仅根据 CPU 高就把全部耗时归因于预览或 Rust。

### 2.2 推荐分两步推进

**第一步：限制昂贵装饰，保留原生编辑器。**

1. 在大文本上跳过全文正则及全量 span 更新。候选门槛为与现有 core 一致的 **128 KiB UTF-8**，不是 128,000 个 Kotlin 字符；最终门槛、span 数量上限由基准决定。超过门槛仍可完整输入/保存，必要时显示轻量“长笔记使用简化高亮”。现行 spec 的最低高亮要求需先明确大文本降级条款。
2. 小文本装饰可防抖、合并重复更新；主题变化和普通重组不应无条件重扫全文。防抖只作用于展示，**不能延后原来的 300 ms／最长约 1 秒本地提交**，也不能使第一次打开仍先跑完整正则。
3. 需要后台计算时，只处理不可变文本快照；不要在后台直接访问/修改正在编辑的 Editable 或 UI span。主线程应用结果前核对空间、笔记、缓冲版本、主题，丢弃迟到结果；组合输入期间不破坏 composing span、光标、选区和撤销。
4. 先验证跳过装饰后原生布局本身是否仍慢。若仍有瓶颈，再讨论可见范围高亮、长行布局策略或专门的大文本编辑路径，不能提前承诺只改一处就足够。

**第二步：后台解析 + 按块惰性预览。**

1. 将解析和块模型构造移到后台，使用当前文本版本关联结果；可显示可取消的局部加载状态，导航和源码切换保持可用。
2. 对 Markdown 块使用 LazyColumn 或等效的按需布局；键与源位置映射必须能区分重复文本。保留任务勾选对应的绝对源码行，不因分块而改错任务。
3. 一个巨大段落或代码块仍可能单个 item 就很昂贵；需单独预算、分段或受控降级，保留原始文本、链接/代码语义和阅读顺序。解析仅后台化也不保证大量 UI span 的应用足够快。
4. 检查跨块文字选择/复制、滚动定位、切回源码和无障碍。不能通过禁用这些已有能力、截断正文或偷偷降低 1 MiB 上限获得“性能通过”。

[Android 响应性指南](https://developer.android.com/topic/performance/anrs/keep-your-app-responsive)支持将耗时工作移出主线程；[Compose 列表文档](https://developer.android.com/develop/ui/compose/lists)说明惰性布局按需要组合内容。项目锁定 Compose UI/foundation 1.7.5，不由此采用最新文档中的新缓存 API 或升级整个依赖树。

### 2.3 拟验收矩阵与候选预算

以下是讨论目标，尚未写入 spec 或测量通过：

- 保持既有 1,000 条／平均 2 KiB 的普通打开/搜索 P95 ≤200 ms，不降低现行基线。
- 对原大样本及允许上限附近文本，候选目标为 **2 秒内进入可交互源码页**；高亮/预览允许后续渐进完成，需同时记录总完成耗时。主线程长任务和输入延迟另测，不能只看到进度条就计为“可编辑”。目标须在选定参考设备上评估后确认。
- 覆盖 20,000 行标题/列表、单个极长段落、单个长行、大代码块、中英 emoji、任务、CRLF 导入，以及 128 KiB 边界两侧和 1 MiB 上限。相同字节数不同结构分别测试。
- 验证首次打开、连续输入/粘贴/删除、IME、选区、撤销、保存、切换笔记/空间/主题、预览往返及后台恢复。保存后重开精确比对；迟到高亮不得覆盖新输入。
- 正式性能结论在 release 包、记录设备与热/冷状态下每组至少 30 个样本；原 API35、API36 若可用和 arm64 真机分别记录，桌面 Windows/Linux 做回归。暂时缺真机不能填写通过。

## 3. 离线交互：联网操作只影响对应区域

### 3.1 Android 现有路径与问题边界

维护者报告：离线切换 Devices，等待后弹出“网络不可用”，阻塞页面。

源码支持这一交互路径：

1. [AccountSettings.kt](../android/app/src/main/java/app/djhx/memo/AccountSettings.kt) 进入设备页触发 loadDevices；关闭设置和切换 tab 受 `!model.busy` 控制。
2. [MemoModel.kt](../android/app/src/main/java/app/djhx/memo/MemoModel.kt) 的 loadDevices 走通用 action，整个请求期间设全局 busy，失败由 report 写入通用 message。
3. [MainActivity.kt](../android/app/src/main/java/app/djhx/memo/MainActivity.kt) 将 message 显示为 MemoAlertDialog。
4. [CoreGateway.kt](../android/app/src/main/java/app/djhx/memo/CoreGateway.kt) 已把调用放到 Dispatchers.IO；core 普通 HTTP 的连接/总超时为 8/35 秒。**不能将本问题直接诊断为主线程执行网络 I/O**，也不能声称一定等待满 35 秒；已确认的是全局忙碌状态会造成交互等待，实际等待时长受网络失败方式影响。

桌面 openSettings(devices) 也走通用 run/busy，需要回归，但本轮用户明确报告的平台是 Android，没有把桌面也记作已复现。

### 3.2 推荐交互

进入设备页立即切换页面。加载指示、错误、重试都放在设备区域；保留返回、关闭设置、切换其他页和回到笔记编辑的能力，不等待网络超时才释放全局界面。

| 页面状态 | 建议展示与行为 |
|---|---|
| 初次加载、无缓存 | 设备区加载提示，其他导航可用 |
| 无网络/无法连接、无缓存 | 行内“无法连接服务器，设备列表暂不可用” + 重试；不显示为“没有设备” |
| 同账号已有缓存，刷新失败 | 保留列表并标明“上次获取结果／当前无法刷新”，不可暗示实时权威状态 |
| 刷新中 | 只限制重复刷新，已显示内容不闪空 |
| 凭据失效 | 设备区提示重新登录；保留本地笔记，避免反复弹框；云状态仍如实反映鉴权失败 |
| 切页或换账号 | 页面继续响应；旧请求不能回写新空间，也不能在返回编辑后弹出旧错误 |

网络错误不应全部翻译成“设备离线”：系统有网络但服务器超时、DNS/TLS 失败或服务端不可用时，也可能无法获取列表。文案使用已知事实，不能仅依据系统联网指示判断服务端可达。

### 3.3 状态与并发边界

- 设备列表使用独立 loading/error/data/request 状态。首期可仅按 profile 保留内存缓存，注销/移除账号时清除其界面缓存，持久化缓存及其隐私生命周期另行决定；不把账号 A 的设备展示给账号 B。
- 请求绑定 profile、服务器/会话和请求序号；晚到结果、吊销后的旧会话响应不得更新当前页面或取消新会话。复用已有会话安全规则，不能在 UI 重写鉴权或同步规则。
- 离开页面可以取消等待、作废结果并及时释放交互；**取消 Kotlin Job 不保证中断正在 JNI 中执行的 blocking HTTP**。如需真正停止 I/O，应单独设计请求级取消/超时，不用全局取消打断笔记同步或其他请求。
- 页面解除 busy 不等于核心活动已经结束；原生更新安装屏障仍须等待真实 I/O 排空，保存、空间切换、永久删除和安装锁的既有保护不能因拆分 loading 状态被绕过。
- 操作重试合并，不因重组或反复切页启动无界请求；断网时不快速自动重试。缩短请求超时只能改善等待，不能替代状态隔离。
- 吊销等写操作仍需明确确认和服务端成功回执；离线不显示成功、不悄悄排队吊销。不能把所有对话框一概移除，数据破坏/权限确认仍单独处理。
- 扩展检查设备刷新/吊销、登录/注册/注销、手动同步、更新检查/下载等联网入口；本地编辑、搜索、导出始终依赖本地能力。保存失败、账号失效、恢复代次等重要提示保留明确处理入口。

拟验证断网、飞行模式、黑洞连接/慢响应、HTTP 错误、鉴权失效、切页/空间、Activity 重建和联网恢复。网络读请求期间持续返回/切页/编辑，候选交互反馈预算 ≤200 ms；不弹模态网络错误、不丢编辑、不串账号。上述为待验证目标，本轮未做网络故障注入。

## 4. 编辑排版：区分自动折行、源码换行和 Markdown 段落

用户观察有源码依据：桌面 [Editor.svelte](../desktop/src/Editor.svelte) 将整个 scroller 的 lineHeight 设为 1.85；Android SourceEditor 对 EditText 统一 setLineSpacing(0, 1.65)，没有单独的 Markdown 段落间距。

三种情况需要分开讨论：

| 文本结构 | 含义 | 建议 |
|---|---|---|
| 超长单行随窗口折成多行 | 同一个源码行的视觉折行 | 使用普通行高，不插入额外间距或换行 |
| 一次 Enter，下一源码行仍属于同段 | Markdown 通常为段内 soft break，具体硬换行由标记决定 | 不把每个 Enter 都当段落末尾 |
| 空行分隔的真正段落 | Markdown 段落边界，代码/列表等另有规则 | 保留空行与适量段落留白，避免同时叠加很大的空行和 margin |

依据：[CommonMark 段落](https://spec.commonmark.org/0.31.2/#paragraphs)和[软换行](https://spec.commonmark.org/0.31.2/#soft-line-breaks)。这是解释现有文本语义，不要求用户改变保存格式。

**建议先采用保守微调：**桌面行高从 1.85 对比 1.70／1.75，Android 从 1.65 对比 1.60；这些是待比较值。段落仍以真实空行分隔，减少长行折行的松散感，不改变正文/Enter/导出含义。字体与缩放不同，最终按真实中英长文选择，不强求两端数字完全相同。[TextView 行距接口](https://developer.android.com/reference/android/widget/TextView#setLineSpacing(float,%20float))本身设置统一行距，不能自动识别 Markdown 段落。

如果仍不够清楚，再讨论“仅在 Markdown 段落边界增加约 0.3–0.5em 视觉间距”的方案；不能简单给每个源码行加 padding。桌面需要与 CodeMirror 的高度测量/选区协同；Android 可能涉及 paragraph/line-height span 的范围与 IME。代码围栏、列表、引用、空行、连续换行、触摸光标与上下移动都要验收。这会增加 M2 的布局成本，建议在性能方案稳定后决定，不本轮选定新编辑器或富文本模式。

## 5. 图片：可行，但完整支持涉及数据与同步边界

当前 [product-v1](../spec/product-v1.md) 暂缓附件，并禁用外部图片自动加载；两端也没有可靠的托管图片同步。Markdown 有图片引用语法，不等于应用已支持图片。维护者本轮授权的是可行性讨论，不改变这一现状。

| 方向 | 能获得什么 | 主要限制 | 初步判断 |
|---|---|---|---|
| 外部 HTTPS 图片，用户主动加载 | 较小范围的预览能力 | 第三方请求、离线不可用、链接失效；缓存与追踪边界需定义 | 可选先行方案，但不自动加载，也不冒充本地优先图片能力 |
| 直接引用设备路径/SAF URI | 当前设备访问现有图片 | 其他设备不可用、授权会失效、导出不完整 | 不建议作为正式跨端图片方案 |
| 应用托管图片，私有本地副本 + 鉴权同步 | 截图/照片可离线插入，跨设备完整阅读 | 新增附件模型、文件队列、协议、存储/配额、备份与导出，范围较大 | 若目标是日常跨端插图，推荐单独里程碑设计 |

建议的真实目标是“把一张截图/照片插入笔记，断网可见，联网后另一端也能看到”。如果只需要外链预览，范围和交互可以明显缩小；拍照、OCR、绘图和通用附件不默认捆绑。

托管方案至少先确定：

1. 图片使用稳定资产 ID、账号范围和内容校验；笔记正文只保存引用，不把 base64 塞进现有 1 MiB 文本。图片本地提交与引用不能出现“显示保存成功但源文件未持久化”。不依赖原始外部绝对路径。
2. 未登录空间也能本地插入；复制到账号空间时连同图片和映射一起处理。图片上传/下载独立于编辑，引用先到时显示明确占位/重试，不能无限阻塞笔记同步或误报全部已同步。需可靠持久队列、幂等、崩溃恢复及先后顺序，不能用 UI 布尔值代替。
3. 先限定静态栅格格式及字节数/像素数/解码内存预算，讨论缩略图、原图保留与 EXIF 处理；SVG、动图、任意 HTML/data URI 不默认开放。具体库、许可证、维护来源与版本确定后另补 ADR，本文不选入新依赖。
4. 服务端按账号鉴权并校验大小/类型/哈希，设置存储配额；不默认全局跨账号去重或代理任意远程图片 URL。客户端不向外部图片地址附加应用 token。
5. 普通删除、永久删除、共享引用和孤立文件的保留/清除规则必须明确；不能借图片引入未批准的自动清理。备份/恢复覆盖数据库和文件的一致性，旧客户端能力协商与迁移路径另定，不能继续宣称现有协议/schema 原样足够。
6. 空间 ZIP 应打包资产和可移植相对引用；单篇 `.md` 如何携带配图需要另选“Markdown + assets 目录”或打包方式。不能沿用“单文件正文完整”措辞却悄悄漏掉图片，也不默认破坏 0.1.10 单篇精确文本导出的契约。

上述跨 core/server/Android/desktop、协议与运维边界，需要专门 spec/ADR、共享场景和独立同步/迁移/鉴权评审。**建议下一版先解决 M2/离线；图片完成需求与协议设计后再确定实现版本。**

## 6. 图标：桌面构图与墨绿候选分别比较

维护者满意 Android 和托盘；它们作为已接受的视觉基准保留。本轮已查看[设计板](../assets/brand/design-sheet.png)及桌面 128px PNG：sunrise 为满幅圆角橙渐变，中心墨盘较小。源 master.svg 按几何估算，墨盘可见直径约占画布 42%；这不是操作系统截图测量，Android 自适应遮罩/缩放后的占比也不能直接与 PNG 数字等同。

建议未来设计比较保持同一个墨盘/缺口/墨滴图形，分开改变两个变量：

| 候选 | 构图 | 背景/前景 | 用途 |
|---|---|---|---|
| A | 原 sunrise，中心图形增至约 55% | 现有橙渐变/墨色盘/浅色滴 | 先确认问题是否主要来自图形过小 |
| B | 中心图形增至约 60% | 同 A | 比较视觉重量与小尺寸细节 |
| C | 与选中的 A/B 同构图 | 墨绿渐变候选 `#224D3E → #102D25`，浅暖盘 `#F6F1E7`、绿底色墨滴 | 比较与现有品牌绿、纸白/炭灰界面的协调性 |

这些都是**设计候选参数，没有生成、替换或验收图形资产**。墨绿可能与主界面绿系更一致，但这是审美判断；深绿底上继续用近黑盘容易辨识不足，因此建议同时比较反色浅暖盘。原墨盘是否必须保持黑色也留待看稿决定。

后续先做桌面 16/24/32/48/64/128/256px 的实际尺寸稿，再在 Windows 快捷方式、任务栏、安装器和 Linux dock/菜单的浅深背景比较，不能只放大一张 1024px 图。小尺寸允许光学调整，不能简单统一放大后裁掉缺口或墨滴。

墨绿只用于桌面还是统一彩色品牌，是待定项；**没有授权自动更换满意的 Android/托盘**。任何平台差异也须记录在同一份版本化品牌输入与平台映射中，按[品牌更新流程](brand-change-workflow.md)归档，不手改生成 PNG/ICO，也不改 app ID 刷缓存。现有素材包有五套配色，但没有这套墨绿，不能当成已存在的现成资产。

## 7. Windows 安装目录：新安装随语言，升级认旧路径

### 7.1 已核实的现状

[installer.nsi](../desktop/src-tauri/windows/installer.nsi) 的窗口 Name 使用 MemoBrandName，已可按安装语言显示新品牌；但 INSTALLIDENTITY 固定为“简记”，同时用于兼容注册表身份和默认目录，首次 currentUser 安装默认落到 `$LOCALAPPDATA\简记`。RestorePreviousInstallLocation 从旧注册表读取已安装路径。

因此用户看到默认目录仍有“简记”有代码依据；不能把它扩大成安装器所有可见名称都仍是旧名。固定身份保留是 0.1.10 的兼容决定，参见[品牌规范](brand-guidelines.md)及[0.1.10 契约](../spec/client-0.1.10.md)。

### 7.2 对维护者想法的建议

**按安装语言设置新装默认目录是合理的，建议仅作用于没有既有安装、没有明确自定义路径的情况：**

| 场景 | 候选目录规则 |
|---|---|
| 首次安装，English | `$LOCALAPPDATA\djhxmemo` |
| 首次安装，简体中文 | `$LOCALAPPDATA\阳墨随记` |
| 已安装旧版，目录为“简记” | 原目录覆盖升级 |
| 已安装于用户自定义目录 | 原目录覆盖升级，不随安装语言搬动 |
| 新装显式选择目录或传 `/D` | 尊重用户指定路径；具体命令行优先级需测试 |
| `/UPDATE`、静默/被动升级、修复安装 | 找到既有安装时沿用路径，不重新按语言计算 |

显示名仍为 DJHX MEMO／阳墨随记；英文目录 djhxmemo 没有空格，且与中文目录都可以作为新默认值。不要让应用设置中的语言切换移动安装目录。若未来需要把旧安装也迁移新目录，单独设计退出进程、移动失败恢复、快捷方式与卸载信息更新流程，不混入本次默认目录微调。

实现时应把“新装默认目录名”和“兼容安装识别键”分离：旧 INSTALLIDENTITY/卸载键仍用于识别同一产品，binary、identifier、数据目录、keyring/Keystore、更新公钥/证书不变；不能全局替换“简记”。当前 spec/品牌检查固定旧默认路径，需先追加下一版契约并调整明确的校验，不能通过关闭检查绕过它。

拟测试英文/中文新装、旧简记覆盖、自定义路径、切换安装语言重装、`/D`、`/UPDATE`、`/NS`/静默、快捷方式冲突、卸载与原笔记/凭据保留。保持一个安装识别记录，不能留下两套卸载入口。[NSIS InstallDir 文档](https://nsis.sourceforge.io/Reference/InstallDir)说明默认目录与浏览选择的行为；项目旧路径兼容的具体结论来自当前模板，而非通用文档。
