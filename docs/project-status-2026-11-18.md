## 0. 一页结论

1. **产品已能用，但还没有达到 v1。** 阳墨随记（DJHX MEMO）已公开发布 0.1.10，Windows、Linux、Android 三端客户端均已发布并具备记笔记和同步能力。连续 7 天的日常试用已由维护者确认完成且未发现阻断问题；该确认不替代三端真机矩阵。v1 目前剩下的硬门槛是三端真机的完整验收和 15 项发布清单，三端真机矩阵尚未完成、15 项清单仍未勾选，0.2.0 计划里也没有安排。
2. **有两件事有截止日期：**
   - **2026-12-14 之前**必须重新签发"自动更新目录"，否则 Windows 和 Android 的自动更新会全部停止。
   - **2026-12-27** 服务器 HTTPS 证书到期，仓库里没有自动续期的记录。
3. **本次检查发现 4 个值得优先修的新问题：**
   - 某种时机下，一篇笔记会永久停止同步，用户自己无法恢复。
   - 桌面端按 Ctrl+Z 可能悄悄覆盖另一台设备的修改。
   - 服务器的登录防护可以被人为填满，导致所有人都登录不了。
   - 服务器重启后，客户端的自动同步会停下来，要手动点一次同步才恢复。

   此外，已知的"大笔记卡顿"（Android 上打开约 1MB 的笔记要卡两分多钟）仍是用户体验最差的一点。
4. **0.2.0 计划同时做五件事，范围偏大。** 建议拆成两个版本："体验修复版"和"图标与安装目录版"。
5. **CLI（命令行版本）调研：建议暂不立项。** 调研文档里有内网 IP 和用户名，合并前必须删除。

## 1. 这个项目是什么（非技术说明）

一个给维护者本人和少数受邀朋友用的 Markdown 笔记软件。断网也能写，联网后自动同步到自己的服务器。

| 组成部分 | 通俗理解 | 当前版本 |
|---|---|---|
| core（核心库） | 每台设备里的"笔记管家"，负责本地存储、排队待上传的修改、同步和处理冲突。三端共用同一份代码 | 0.1.10 |
| server（服务器） | 云端的"总账本"，负责账号、每篇笔记的权威版本，以及实时通知其他设备 | 0.1.4（从 0.1.4 起没有改动） |
| desktop（桌面端） | Windows / Linux 应用 | 0.1.10 |
| android（安卓端） | 手机应用 | 0.1.10（versionCode 11） |
| website（官网） | memo.djhx.site 介绍和下载页 | 跟随客户端 |
| 同步协议 / 数据库结构 | 设备和服务器之间的"沟通语言"和数据格式 | 协议 2 / 结构 3，0.1.4 后未变 |

模块版本号不一致是正常的：只有改动的部分才升级版本。

## 5. 存在的问题（按优先级）

### 5.1 本次检查新发现、建议优先处理

| # | 问题（通俗描述） | 影响 | 平台 | 已核实 |
|---|---|---|---|---|
| A | **笔记永久停止同步**：设备上传笔记的那一刻，如果恰好被吊销、改了密码或登录到期，这篇笔记会被永久标为"阻塞"，以后的修改都不会再上传，重新登录也恢复不了 | 数据只留在本机，用户不知情或无法自救 | 三端（核心库 + 服务器） | ✅ 我已在源码中确认触发路径和"没有解除路径" |
| B | **Ctrl+Z 覆盖他人修改**：另一台设备的修改同步到桌面编辑器后，按 Ctrl+Z 会把这次同步撤掉，旧内容随后被保存并同步出去，系统不提示冲突 | 其他设备上的修改被静默覆盖 | 桌面 | ✅ 已确认代码缺少"不进撤销记录"的标记 |
| C | **登录防护可被填满**：服务器记录登录尝试的表有 1 万条上限，用随机用户名就能填满，之后所有人都登录不了、也注册不了，持续约 15 分钟，可以反复触发 | 拒绝服务 | 服务器 | ✅ 已确认代码逻辑 |
| H | **服务器重启后自动同步停摆**：服务器重启或部署的那几秒里，客户端收到网关返回的错误网页，误判为“永久错误”，之后不再自动同步，直到用户手动点同步 | 用户以为在同步，实际没有 | 三端（核心库） | ✅ 已确认代码路径 |
| I | **大笔记同步时反复重建搜索索引**：只改笔记的状态信息也会把整篇正文重新建一次搜索索引 | 加重大笔记卡顿 | 三端（核心库） | ✅ |
| D | **同步期间打字被吞**：桌面端手动同步时编辑器是只读的，网络慢时这段时间的按键会静默丢失 | 输入丢失 | 桌面 | 代码逻辑已确认，实际时长未测 |
| E | **后台持续耗电**：安卓切到后台后仍然每秒查询一次状态；桌面隐藏到托盘后也持续轮询 | 耗电，Linux 上频繁启动子进程 | 安卓、桌面 | ✅ |
| F | **列表每次读取全部正文**：搜索每输入一个字、每次保存，都会把所有笔记的正文读一遍 | 让大笔记卡顿更严重 | 安卓（核心库） | ✅ |
| G | **密码框没有声明"密码键盘"**：输入法可能学习或联想密码和邀请码；登录失败会清空密码，错误还是弹窗提示 | 隐私、体验 | 安卓 | ✅ |

### 5.2 已知问题（之前的审计已记录）

- **M2 大笔记卡顿（最严重的体验问题）**：在安卓模拟器上打开一篇约 940KB、2 万行的笔记，界面卡死约 135 秒。这个大小在允许范围内。已纳入 0.2.0。本次还发现桌面端每按一个键也会把整篇全量重新渲染，大笔记同样有卡顿风险。
- **安卓离线时打开"设备"页会锁住界面**：要等网络超时后弹窗报错。已纳入 0.2.0。
- M1 和 L1～L6：若干低级别候选问题，没有排期。上面的问题 A 是 M1 一直缺少的"真实触发路径"，建议把 M1 提级。

### 5.3 协议文档与实现不一致

服务器实际返回的一些错误码和接口文档写的不一样，例如游标格式错误应返回哪个错误码，几种拒绝请求的场景也没写进文档。目前不影响用户。但这三份文档（spec 说明、OpenAPI、错误码表）是"唯一事实来源"，建议补齐。

## 8. 两个调研分支的结论

### `codex/docs-client-020-predevelopment`（0.2.0 开发准备）

- **质量好**：不改正文语义、不改应用身份、不在界面层重写同步规则，这些边界写得清楚；坚持"先测量再优化"。
- **问题**：
  - 五项范围混在一个版本里（见决策 3）。
  - 验收标准还不能度量。
  - spec 草案里仍有"建议""候选"这类未定措辞。
  - 讨论稿正文与最终决定相互矛盾：正文仍写着"保留安卓图标"，只在页首用一句话推翻。
  - 图标工作量被低估：现有工具渲染不了 jade SVG，需要完整资源包或新工具。
- **建议**：可以合并，但合并前把讨论稿中已被推翻的段落标为"已废止"。

### `research/cli-cross-platform`（命令行版本调研）

- **结论**：技术上可行（已在 Linux / Windows 跑通基本命令），但**不建议现在立项**。理由：
  1. v1 还没完成，CLI 相当于"第四端"，打包、更新、测试都要多一份。
  2. 程序名 `djhx-memo` 和 Linux 桌面版重名，安装时会互相覆盖。
  3. CLI 和正在运行的桌面应用同时读写同一个数据库、同时同步，可能出问题，规范里没有写。
  4. 在没有系统密码库的服务器上，登录后凭据马上丢失，账号功能实际不可用。
  5. 新增依赖没有写 ADR。
- **必须处理**：调研文档里写有内网 IP（192.168.122.x）、用户名和本机路径，**不能合并进公开仓库**。另外，`spec/cli.md` 放在"唯一事实来源"目录下，容易被误当成已接受的契约，建议移到 `docs/research/`。

## 9. 流程与治理观察

- **没有 CI**（2026-11-18 时项目明确决定不建；2026-11-19 起改为采用 GitHub Actions，见 [ADR-0017](adr/0017-github-actions-ci.md)）。所有检查在本机手动执行并写入文档。文档纪律很好，"测过"和"没测过"分得很清楚。
- **单人项目风险**：开发、发布、签名私钥、备份接收端、Windows 验收都集中在维护者一个人和一台电脑上。
- **服务器单实例**：一台主机、一个 SQLite 数据库，没有热备；故障只能靠备份恢复。
- **好的方面**：
  - 安全基础扎实：密码用 Argon2id；令牌只存哈希；更新包有签名校验和防回放。
  - 安卓禁止了备份导出，正文不进日志，Git 历史中没有发现泄露的密钥。

## 附：术语小词典

| 术语 | 含义 |
|---|---|
| spec | 产品行为的"法律条文"，代码必须与之一致 |
| ADR | 架构决策记录，引入新技术或依赖时要写 |
| 同步协议 | 设备和服务器之间交换笔记的规则 |
| outbox / 待发送队列 | 本机还没上传成功的修改排成的队 |
| 墓碑 | 笔记被删除后保留的"已删除"标记，让其他设备知道它被删了 |
| 交叉评审 | 由另一个人或代理独立检查高风险改动 |
| 更新目录 | 服务器上一份带签名的"最新版本清单"，客户端靠它判断要不要更新 |
| arm64 真机 | 普通安卓手机；模拟器通常是 x86，表现不同 |
