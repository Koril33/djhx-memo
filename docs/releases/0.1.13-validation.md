## 1. 发布前核实的既有风险

### 1.1 更新目录 `schema_min`/`schema_max` 与本地 schema 4（核实结论，2026-11-21）

早期评估把"目录 `schema_min`/`schema_max` 仍为 3、笔记库已为 4"列为待澄清风险。核实 `core/src/update_catalog.rs` 后结论如下：

- `validate_release`（[update_catalog.rs:794-797](../../core/src/update_catalog.rs)）把 `schema_min`/`schema_max` **硬编码校验为必须等于 3**（`r.schema_min != 3 || r.schema_max != 3 → UPDATE_INCOMPATIBLE`），注释明确"首版刻意拒绝跨协议/schema 升级"。
- 全仓库没有任何代码把客户端 `PRAGMA user_version`（现为 4）与目录的 `schema_min`/`schema_max` 比较——这两个字段被声明、被硬编码校验、然后不再被读取。
- 因此目录生成器写 `3`、校验器检查 `==3` 是自洽的；客户端本地 schema 4 不参与该检查。**该不一致不会阻断自动更新**。
- 遗留问题是目录范围字段尚未接到真实user_version门禁，不能据此断言所有schema保护都不存在：`db::open`仍拒绝高于自身迁移版本的库。当前两个3属于固定兼容标记，不能改称“目录格式版本3”（信封/payload另有格式版本）。后续应澄清字段语义；若接入真实库范围检查，需单独设计旧更新器兼容桥接，不能直接把目录数字改成4。
